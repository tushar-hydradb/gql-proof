# prior art for gql-proof's next steps: research report

*generated 2026-10-20 | about 110 sources reviewed across 4 research agents, roughly 20 deep-read | confidence: high on what exists, medium on negative results ("nobody does X")*

## summary

- **closest prior art: the kaist line for ecmascript.** jisetd/esmeta mechanize the spec, jest (icse 2021) generates conformance tests from it, and feature-sensitive coverage (pldi 2023) refines coverage by the innermost enclosing language feature, k-limited. that is our cdrc/k-path idea applied to javascript
- **what that line does not do.** it generates valid programs only. it claims coverage percentages and bugs found, never conformance. it has no must-reject tests, and it does not report targets that are semantically infeasible
- **what we can reuse.** a lot of what the roadmap still has to build exists in pieces:
  - grammar-mutation negatives on top of purdom (raselimo et al. 2019)
  - test262's and wasm's way of labelling negative tests
  - xsmith's attribute-grammar tricks for scope and types
  - dinkel's state model for graph queries
  - mgql and gpml-conformance as executable oracles
  - xdata/qagen-style solver-built test data
  - cedar's way of separating what is proved from what is tested
- **genuine gaps, i.e. where gql-proof is new:**
  1. feature tags extracted mechanically from the iso conformance rules
  2. coverage defined over the semantically valid sublanguage, with infeasible targets reported as such
  3. negatives that break exactly one syntax rule, with the verifier confirming nothing else broke
  4. graph test data generated to meet a coverage goal
  5. an executable oracle for the general rules' exception conditions
  6. a conformance claim indexed by feature and qualified by stated hypotheses

## 1. feature tagging and negative tests

**mapping features to grammar.**
- sql has been split into features at the grammar level before. sql à la carte decomposed the sql:2003 bnf into hundreds of features and composed parsers per feature selection ([rosenmüller et al., btw 2009](https://www.se.cs.uni-saarland.de/publications/docs/BTW2009sql.pdf)). that was by hand, not tied to iso feature ids, and generated no tests. high
- cide only lets you tag parts of a grammar that are already optional, so removing a feature never produces broken syntax ([kästner et al., tools europe 2009](https://doi.org/10.1007/978-3-642-02571-6_11)). high. our tags should follow the same discipline: a feature tag lands on an optional element or an alternative, and the claimed-feature refinement deletes exactly those
- no prior work turns iso-style "without feature X, conforming language shall not contain <nt>" rules into grammar annotations automatically. medium, a negative result

**how suites declare features and negatives.**
- **test262** puts metadata in each test's front matter:
  - `features: [...]` draws from a closed vocabulary file
  - `negative: {phase, type}` says when the error must happen (parse, resolution or runtime) and which error it must be
  - parse-phase negatives call `$DONOTEVALUATE()` to catch accidental execution

  ([test262 interpreting.md](https://chromium.googlesource.com/external/github.com/tc39/test262/+/refs/heads/master/INTERPRETING.md)). high
- **webassembly** separates `assert_malformed` (does not parse) from `assert_invalid` (parses, then fails validation) ([wasm interpreter readme](https://github.com/WebAssembly/spec/blob/main/interpreter/README.md)). high
- **xquery's qt3 suite** has feature dependency values that drifted away from the spec's actual optional features, until a catalog check was added ([w3c bug 21314](https://lists.w3.org/Archives/Public/public-qt-comments/2013Mar/0053.html)). medium. the lesson is to derive the vocabulary mechanically, from `features.xml` in our case

**generating negatives.**
- raselimo, taljaard and fischer generate inputs guaranteed to be outside the language from first/follow/precede sets:
  - "poisoned pair" token edits
  - rule mutations kept only when an item condition holds

  a 2019 lund report implements this on top of purdom (neotestgen) ([sle 2019](https://conf.researchr.org/details/sle-2019/sle-2019-papers/16/Breaking-Parsers-Mutation-based-Generation-of-Programs-with-Guaranteed-Syntax-Errors); [johansson 2019](https://fileadmin.cs.lth.se/courses/edan70/CompilerProjects/2019/Reports/Johansson.pdf)). high on the mechanism, which was read second-hand
- eris enumerates ill-typed programs with one injected error each, and handles "silent repair", where inference quietly makes the injected error valid again ([sotiropoulos & su, pldi 2026](https://pldi26.sigplan.org/details/pldi-2026-papers/77/Enumerating-Ill-Typed-Programs-for-Testing-Type-Analyzers)). high. our counterpart: breaking one syntax rule can land the tree in a different valid derivation, so the verifier must confirm exactly one rule fails
- hephaestus gets negatives by overwriting a type in a well-typed program ([chaliasos et al., pldi 2022](https://pldi22.sigplan.org/details/pldi-2022-pldi/2/Finding-Typing-Compiler-Bug)). high

**feature interactions.**
- t-wise sampling over feature models is mature:
  - [medeiros et al., icse 2016](https://arxiv.org/abs/1602.02052)
  - yasa ([vamos 2020](https://doi.org/10.1145/3377024.3377042); authors not verified)
  - t-wise presence-condition coverage, where the "artifacts" can be our productions ([krieter, thüm et al., arxiv 2205.15180](https://arxiv.org/abs/2205.15180))

  no published criterion combines these with cdrc or k-paths. medium

## 2. semantically valid generation that keeps coverage

**the generator techniques converge.**
- generate top-down against an expected type and an environment ([pałka et al., ast 2011](https://research.chalmers.se/en/publication/145797))
- or derive the generator from the type system itself:
  - from plt redex judgments ([fetscher et al., esop 2015](https://conf.researchr.org/details/esop-2015/esop-2015-papers/1/Making-Random-Judgments-Automatically-Generating-Well-Typed-Terms-from-the-Definitio))
  - from coq inductive relations, with soundness and completeness proofs ([lampropoulos et al., popl 2018](https://popl18.sigplan.org/details/POPL-2018-papers/11/Generating-Good-Generators-for-Inductive-Relations))

high

**xsmith** ([hatch et al., gpce 2023](https://2023.splashcon.org/details/gpce-2023-papers/7/Generating-Conforming-Programs-With-Xsmith)) brings four ideas we want:
- per-production type rules
- choice predicates that drop productions illegal in the current context
- scope graphs
- **lifting**: when a reference has nothing to bind to, create the binder upstream instead of discarding the tree

its docs admit the analysis is conservative, so some valid programs are never generated. high

**coverage plus constraints is the open seam.**
- isla uses k-path coverage only as a penalty in its search, not as a target set ([steinhöfel & zeller, fse 2022](https://2022.esec-fse.org/details/fse-2022-research-papers/61/Input-Invariants)). high
- fandango replaces isla's solver with a genetic one that is 1 to 3 orders of magnitude faster ([issta 2025](https://conf.researchr.org/details/issta-2025/issta-2025-papers/40/FANDANGO-Evolving-Language-Based-Testing)). high
- "language-based protocol testing" targets uncovered k-paths with an a* navigator and fandango's constraint solving ([arxiv 2509.20308](https://arxiv.org/abs/2509.20308)). but it counts coverage over all trees, valid or not, and admits targets stay unreached when constraints fail. high
- van heerden et al. combine grammar coverage with scope and type markers, and throw away tests that cannot be completed ([sle 2020](https://2022.splashcon.org/details/splash-2022-sigplan-papers/32/Grammar-based-testing-for-little-languages-an-experience-report-with-student-compile))
- goldstein et al. measure combinatorial coverage over well-typed generators ([esop 2021](https://link.springer.com/chapter/10.1007/978-3-030-72019-3_10))

**nobody defines cdrc or k-path coverage relative to the well-typed sublanguage, or separates "uncovered" from "infeasible".** medium-high

**graph query generators.**
- gdsmith keeps a per-clause environment and regenerates a subtree when no variable fits. it reaches 100% validity on neo4j, and concedes grammar coverage does not tell the tools apart ([hua et al., issta 2023](https://arxiv.org/abs/2206.08530)). high
- dinkel splits state in two ([wüst, jiang, su, pvldb 19](https://www.vldb.org/pvldb/vol19/p1198-jiang.pdf)). high, and the best model for gql's scoping:
  - a scoped query context of typed variables, pushed and popped by clause, `CALL` and `UNION`
  - a persistent graph schema
- no gql-specific generator was found. medium

**static semantics to filter or cross-check with.** mgql's type checker is certified and its schema model is reusable: closed graph schemas, node and edge schemas, nullability, union and list types. but it takes lean `Query` terms, not query text, and covers only the read-only core ([mgql](https://github.com/EngineeringSoftware/mgql)). high

**cedar pairs two generators** ([disselkoen et al., fse 2024](https://arxiv.org/html/2407.01688v1)). high:
- a type-directed one: schema, then entities, then policies
- a schema-respecting but ill-typed one, for error paths

## 3. oracles and test data

**what can actually execute.**
- mgql (lean, read-only core):
  - covers set operators, three-valued logic, `TRAIL`, `COUNT`/`SUM`/`MAX`/`MIN`
  - excludes `WITH`, `OPTIONAL`, `ORDER BY`/`LIMIT`, shortest paths, and seemingly `LET`, `FOR`, `NEXT`, `CALL` and updates
  - needs an emitter from our trees to lean terms
- gpml-conformance (python, path patterns): restrictors, selectors, quantifiers, a four-way verdict (conforms, diverges, rejects, inexpressible), and the standard's six worked examples as a sanity gate ([arxiv 2609.23032](https://arxiv.org/abs/2609.23032); [repo](https://github.com/samyama-ai/gpml-conformance))
- the cypher semantics ([sigmod 2018](https://www.pure.ed.ac.uk/ws/files/56321692/cypher_sigmod18_crc_1.pdf)) and gpc ([pods 2023](https://arxiv.org/abs/2210.16580)) exist on paper only

high. **neither runnable oracle models the general rules' exception conditions**, which is half of our totality claim. medium

**the sql precedent to copy.** guagliardo and libkin validated an executable sql semantics on over 100k random queries against real engines, and used the standard to settle disagreements ([pvldb 2017](https://www.pure.ed.ac.uk/ws/files/46755003/Guagliardo_Libkin_2017_A_Formal_Semantics.pdf)). high

**metamorphic and differential oracles check consistency, not conformance:**
- tlp, norec and pqs
- [gdbmeter](https://2023.issta.org/details/issta-2023-technical-papers/4/Testing-Graph-Database-Engines-via-Query-Partitioning)
- [graphgenie](https://conf.researchr.org/details/icse-2024/icse-2024-research-track/20/Detecting-Logic-Bugs-in-Graph-Database-Management-Systems-via-Injective-and-Surjective)
- [gamera](https://seclab.cse.cuhk.edu.hk/papers/vldb24-graph-db.pdf)
- dinkel
- [eet](https://usenix.org/conference/osdi24/presentation/jiang)

high. use them for breadth, and label anything they back as "consistent", never "conformant"

**equivalence provers.**
- sql's are mature: [cosette](https://www.cidrdb.org/cidr2017/papers/p51-chu-cidr17.pdf), [spes](https://arxiv.org/abs/2004.00481), [sqlsolver](https://par.nsf.gov/biblio/10548354), [qed](https://vldb.org/pvldb/vol17/p3602-wang.pdf), [verieql](https://par.nsf.gov/biblio/10543008) with bounded counterexamples
- for graphs there is only graphqe for cypher ([arxiv 2504.15742](https://arxiv.org/abs/2504.15742)). medium

**test data.**
- sql has query-aware generators:
  - [qagen](https://se.ifi.uni-heidelberg.de/fileadmin/pdf/publications/2007_QAGen_Sigmod.pdf), [reverse query processing](https://dsl.cds.iisc.ac.in/~course/TIDS/papers/rqp.pdf), [qex](https://www.microsoft.com/en-us/research/publication/qex-symbolic-sql-query-explorer-2/)
  - [xdata](https://arxiv.org/abs/1411.6704) builds mutant-killing datasets with a solver
  - [evosql](https://serg.ewi.tudelft.nl/publications/search-based-test-data-generation-for-sql-queries/) is search-based
- [sqlfpc](https://giis.uniovi.es/testing/papers/stvr-2010-sqlfpc.pdf) gives an mc/dc criterion for sql that includes null
- **no property-graph data generator meets a coverage goal**; gdsmith and dinkel only avoid empty results. medium

**value partitions.**
- [category-partition](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/ostrandCategoryPartition88.pdf) and [sql mutation operators](https://digibuo.uniovi.es/dspace/bitstream/10651/29255/2/ist-2006-sqlmutation.pdf) apply directly
- type conversion is a live bug class: 37 bugs across 6 dbmss ([typecheck, pvldb 2026](https://rmarcus.info/dbscholar/papers/h5a771965c78807ba)). high

## 4. making the claim rigorous

**test hypotheses, precisely** ([gaudel & le gall 2008](https://arxiv.org/abs/0804.0970), deep-read). high:
- under a minimal testability hypothesis, passing the exhaustive test set is equivalent to correctness
- uniformity and regularity are the two selection hypotheses
- the oracle is an observability hypothesis: only observable sorts are compared, which here means result tables and gqlstatus codes

so our claim takes the form "h_min and h1..h5 imply that passing t means conformant for f"

**no completeness theorem exists for grammar-derived test sets.**
- fsm testing has complete suites for fault domains ([vaandrager et al., concur 2025](https://arxiv.org/abs/2410.19405))
- grammars only have coverage criteria
- rule coverage alone predicts fault detection weakly ([hennessy & power 2008](https://link.springer.com/article/10.1007/s10664-008-9067-7))

medium. a "k-path is complete for fault domain d_k" result would be a contribution; until then, h1 is an assumption

**bounded-exhaustive testing claims bugs found, or holds for everything up to a bound.**
- [astgen](https://ideals.illinois.edu/items/11331) and [udita](https://infoscience.epfl.ch/record/146525) claim bugs found
- roberson et al. claim type soundness for all states up to size n ([oopsla 2008](https://web.eecs.umich.edu/~bchandra/publications/oopsla08.pdf)), the template for wording a bounded claim

high

**the templates.**
- **cedar** keeps three things apart:
  - what is proved in lean about the model
  - what differential testing shows, which is evidence the code matches the model
  - an explicit list of what is not modelled (the parser, malformed inputs)

  it also says "complete line coverage alone does not guarantee effective testing". high
- **compcert**: csmith found wrong code only in the unverified front end. medium, secondary sources only
- **specTec and wasmcert** validate the spec against the official suite, not implementations ([pldi 2024](https://pldi24.sigplan.org/details/pldi-2024-papers/64/Bringing-the-WebAssembly-Standard-up-to-Speed-with-SpecTec))

**beyond the bound.**
- report residual risk with bias-corrected discovery-probability estimators ([böhme et al., fse 2021](https://2021.esec-fse.org/details/fse-2021-papers/39/Estimating-Residual-Risk-in-Greybox-Fuzzing); [stads](https://arxiv.org/abs/1803.02130)). naive estimators systematically underestimate the risk. high
- mutation score is a validated proxy for real faults ([just et al., fse 2014](https://homes.cs.washington.edu/~mernst/pubs/mutation-effectiveness-fse2014-abstract.html)). high

**how existing suites report results:**
- [test262 tr/104](https://www.ecma-international.org/wp-content/uploads/ECMA_TR-104_2nd_edition_december_2016.pdf), xqts, sparql's earl reports and the opencypher tck all disclaim certification
- sql conformance has been self-declared since nist stopped in 1996
- vendors publish per-feature gql tables, e.g. [fabric](https://learn.microsoft.com/fabric/graph/gql-conformance)

**no published work claims spec conformance from grammar coverage plus reference semantics.** medium

## key takeaways for the roadmap

1. **feature tagging (next).**
   - extract tags mechanically from the conformance rules and check them against `features.xml` (the qt3 lesson)
   - put tags only on optional elements and alternatives (the cide discipline)
   - add negatives in the same step:
     - raselimo poisoned pairs and rule mutation on top of purdom, for parse-level negatives
     - one unclaimed-feature subtree per tree, for "feature not supported"
     - negating one compiled syntax-rule automaton, verified to break exactly that rule
   - label every negative test262/wasm style: `{phase: parse | syntax-rule | feature | runtime, status: <class>}`
2. **context provider.** three sources point the same way:
   - extend our product construction with a **finite abstraction** of the environment: typed variable slots, and the expected type of each expression slot
   - assign concrete names late, with **xsmith lifting** instead of discarding
   - follow **dinkel's context/schema split** for scoping, one rule per gql clause
   - use **mgql's schema model** for the catalog

   then define cdrc and k-paths on the typed grammar and report infeasible targets separately. that last part is the clearest novel contribution
3. **oracle.** tiers, with each test tagged by the tier that backs it:
   - a. reference execution: mgql through a rust-to-lean emitter for the core, gpml-conformance for paths, cross-checked where they overlap
   - b. hand-written general-rule tables for everything else, **including exception conditions, which no existing oracle covers**
   - c. metamorphic checks, reported as consistency only
4. **data.** solver-built minimal graphs per query and partition (xdata and qex, with z3), plus hand-picked shapes: self-loops, parallel edges, short cycles, disconnected parts. use sqlfpc's mc/dc with null as the adequacy criterion. nothing like this exists for graphs
5. **the claim.**
   - use cedar's structure: proved, tested, not modelled
   - use bgm's form: hypotheses h_min and h1 to h5, each marked proof, construction or evidence
   - key it to annex d feature ids
   - report per feature: test count, syntax and semantic coverage, mutation score, residual risk, and per-test outcomes
   - cite jest and feature-sensitive coverage as the nearest prior art, and differentiate on hypothesis discharge, negatives and infeasibility reporting
