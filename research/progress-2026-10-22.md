# gql-proof: where we are, 2026-10-22

gql-proof generates gql queries that cover the iso grammar production by
production, so an engine run against them says which parts of gql it handles.
the goal is totality: every production and every production in context
covered, or shown impossible, at a fixed number of variables that we have
argued is enough

## what changed this week

- queries used to only follow the grammar. now every variable is bound before it
  is used, and every expression is typed (numbers where numbers go, nodes where
  nodes go), at up to 2 variables at once
- the typed run at 2 variables finishes in about 11 minutes. a week ago it did
  not finish at all. 3 variables is the next target
- we counted every syntax rule in the standard against what the generator
  enforces, so the open work is a list now, not a feeling

## turbolay, #243 at 484d1a72

the first run had only scoping, the second has types too:

- scoping only: 295 of 790 queries accepted
- with types: 1,174 of 2,243 accepted (52%)

where the other 1,069 went:

- 488 are invalid queries on our side, refused correctly. two rule families we
  don't enforce yet make almost all of them: an EXISTS body has to produce a
  table (`EXISTS { FINISH }` does not), and a path pattern has to match at
  least one node (`MATCH <- ?` may not)
- 282 are turbolay parse gaps: typed VALUE definitions with node, edge or record
  types (242), and KEEP after a graph pattern inside EXISTS (40, new, posted to
  the linear doc of query problems)
- 248 are turbolay's documented deviations, mostly typed VALUE definitions and
  statements outside its typed slice
- 19 raised the data exception the standard asks for, like `DATE ( { } )`
- 17 need parameters our runner doesn't pass
- 15 are bugs already reported

taking out our invalid queries, turbolay's documented deviations and the
missing parameters, turbolay handles 1,193 of 1,490 (80%), and the rest is
almost all the two parse gaps. one earlier report turned out fixed on this
head: a byte string continued across a comment now parses

## static semantics, by the numbers

the standard has 1,025 syntax rules. 482 only define things, and of the 426
that constrain a query or its types:

- 249 are enforced as written
- 91 are enforced more strictly than the standard (we never generate those
  queries, so coverage there is a bit smaller)
- 6 are only checked after the fact
- 80 are not enforced yet

a rule we don't enforce only costs us if the generator can break it, and it
can: empty identifiers, a quantifier bound of 0, `CHAR ( 0 )`, a VALUE body that
isn't one value. that is the 488 above. the catalog dependent rules (66: graph
types, schemas, procedure signatures) are open as a group, since the generator
has no catalog yet

so static semantics is not done, but the work left is listed rule by rule:
`research/static-semantics-inventory-2026-10-22.md`

## what's next

- close the two rule families behind most of our invalid queries, then the
  smaller ones (leaf values like zero lengths and empty names)
- 3 variables, the bound our coverage argument needs for productions
- queries that are valid but always raise at run time, like using a node after
  deleting it. the standard calls that dynamic, we can still spot the sure ones
  statically
